OcteonTX2 RAS implementation
============================

Marvell OcteonTX2 implements the ARMv8 RAS (Reliability, Availability & Serviceability) specification.

This decouples the tracking of hardware exception events from any outage
to the data being transferred, allowing a RAS-aware OS to handle the outage
as it sees fit by analyzing the context in which the data is being used.

Errors in memory, cache, and AP cores are detected by the hardware and handled by ATF
in firmware first mode. Kernel notified via Software Delegated Exception Interface (SDEI).
RAS error records are exchanged between ATF and kernel via a shared memory buffer.
The shared memory layout is described under the Device Tree "sdei-ghes" node.
For layout details of the Device Tree "sdei-ghes" node see the following kernel document:
Documentation/devicetree/bindings/edac/marvell-sdei-ghes.txt

Uboot-based systems utilize Device Tree for communication and set up EDAC framework
driver octeontx_edac for RAS error reporting. On the other hand, ACPI-based systems
do not have access to the Device Tree, and the ACPI table HEST keeps in sync with
the Device Tree by EDK2 firmware and ACPI driver.
For that systems, HEST fully describes shared buffer location, error status block,
and notification type. RAS support for ACPI systems is entirely based
on Kernel mainline APEI, GHES framework. Mentioned shard memory is managed in
a circular buffer manner. RAS error records from the buffer support CPER, GHES
framework layout structure that is maintained by APEI.
The same structure is supported by the EDAC driver for the system that does not support ACPI
but supports EDAC. From a firmware perspective, both RAS reporting schemas look identical.
EDAC driver fulfills the requirement of the framework in the error report, injection,
and corresponding controls and statistics data. For more details, refer to
Documentation/devicetree/bindings/edac/marvell-sdei-ghes.txt and
Documentation/admin-guide/ras.rst
Kernel ACPI-based system works under APEI framework for error report and
uses external module for error injection in future error injection (EINJ) ACPI table
should handle error injection.

RAS error types
---------------
These can be Correctable (CE), Uncorrectable Unrecoverable (UEU)
  CE error is a single-bit ECC error in memory or cache.
  UEU error is a double-bit ECC error in memory or cache.

The uncorrected errors are recorded and are made available to Linux upon subsequent
boot via the Boot Error Record Table (BERT) for ACPI based systems.
Device Tree based systems utilize custom driver otx2-ghes-bert.

The firmware enables exceptions in relevant OcteonTX2 hardware units
LMC, MCC (DRAM Local Memory Controller),
MDC (Memory Diagnostic Controller)
and performs the following actions:
- Capture hardware description of the error
- Convert the hardware description of the error to CPER (Common Platform Error Record) and GHES format
- Collect error records per hardware component ring buffer.
- Make SDEI notification to Kerne driver
- Kernel handles RAS records based on system type ACPI or DT.


Configurations to enable RAS Error Reporting for Device Tree base systems
=========================================================================
Enable module config:
RAS=y
EDAC=y
ARM_SDE_INTERFACE=y
EDAC_OCTEONTX=y
OCTEONTX2_GHES_BERT=y

Configurations to enable RAS Error Reporting for ACPI base systems
==================================================================
Enable module config:
CONFIG_ACPI=y
CONFIG_ACPI_APEI=y
CONFIG_ACPI_APEI_GHES=y
OCTEONTX2_EINJ=y


OcteonTX2 RAS EDAC Error injection LMC/MCC
==========================================

LMC EDAC based interface
cd /sys/devices/system/edac/mc/mc0

EDAC SMC based interface for error injection exemple:
-rw-r--r--    1 root     root         65536 Apr 19 20:15 address
-rw-r--r--    1 root     root         65536 Apr 19 20:15 error_type
--w-------    1 root     root         65536 Apr 19 20:17 inject

echo 0x800000   > address
echo 0x40000300 > error_type
echo 0x1        > inject

address - identify 'physical address' inject error at specified address
			Recommended to use addresses from ASC0 secure region
			1,3,5,7 - spesial case addresses
			1 - predefined kernel data vma virtual address
			5 - predefined kernel code virtual address
			3 - predefined EL3 code address
			7 - predefined EL3 data address

error_type   - parameter describe control flags
			bit 2..0	:  bit position to flip on poisoning write
			bit 3		:  0 = SBE, 1 = DBE
			bit 6..4	:  0 = DRAM, 1 = L1C, cache level to corrupt (L0 == DRAM)
			bit 7		:  0 = D-cache,  1 = I-cache
			bit 8		:  1 = read-back poisoned address in EL3
			bit 9		:  1 = target address EL3-physical, not virtual
			bit 30		:  1 = allow injection

	Injecting DRAM/LMC Single Bit Error (SBE) ECC at physical address 0x800000
	and read-back poisoned content immediately:
	echo 0x800000 > address
	echo 0x40000300 > error_type

	Injecting DRAM/LMC Double Bit Error (DBE) ECC at physical address 0x800000
	and read-back poisoned address immediately:
	echo 0x800000 > address
	echo 0x40000308 > error_type

	Injecting DRAM/LMC Single Bit Error (SBE) ECC at physical address 0x800000
	do not read-back immediately, ECC irq will be triggered after outside 
	read happened:
	echo 0x800000 > address
	echo 0x40000200 > error_type

	Inject DRAM data SBE error at linux kernel predefined virtual address
	echo 1 > address
	echo 0x40000002 > error_type

	Inject DRAM code SBE error at linux kernel predefined virtual address
	echo 2 > address
	echo 0x40000002 > error_type

	Inject DRAM code SBE error at EL3 predefined address
	echo 3 > address
	echo 0x40000002 > error_type

	Inject DRAM data SBE error at EL3 predefined address
	echo 7 > address
	echo 0x40000002 > error_type

cd /sys/devices/system/edac/mc/mc0/
echo 0x800000 > address && echo 0x40000300 > error_type && echo 1 > inject
echo 1 > address && echo 0x40000002 > error_type && echo 1 > inject
echo 2 > address && echo 0x40000002 > error_type && echo 1 > inject
echo 3 > address && echo 0x40000002 > error_type && echo 1 > inject
echo 7 > address && echo 0x40000002 > error_type && echo 1 > inject

EDAC MC0: 1 CE LMC2: DIMM0,R0/0 on  (single-bit ECC addr: 0x800000 card:2 module:0 bank:0 row:32 col:0  page:0x80 offset:0x0 grain:1 syndrome:0x0)

		1 CE - one CE error detected
		single-bit ECC - error type description
		addr: 0x800000 - affected physical address
		card:0 - LMC index
		module:0 - dimm index
		bank:0 - Bank index
		row:64 - row index
		col:0 - Column number
		page:0x80 - Physical page number
		offset:0x0 - Offset in page
		syndrome:0x0 - Unuset currently
		LMC0: DIMM0,R/0) - FRU topology DIMM 0 and Rank left 0, Rank right 0


OcteonTX2 RAS EDAC Error injection MDC
======================================

MDC EDAC based interface
cd /sys/devices/system/edac/mdc/

echo 0x800000 > address && echo 0x10000310 > error_type && echo 1 > inject

	Inject D1 Cache Single Bit Error (SBE) error at address 0x800000:
	echo 0x800000 > address
	echo 0x10000310 > error_type
	echo 0x1 > inject

	Inject D1 Cache Double Bit Error (DBE) error at address 0x800000:
	echo 0x800000 > address
	echo 0x10000318 > error_type
	echo 0x1 > inject

	Inject I1 Cache Single Bit Error (SBE) error at address 0x800000:
	echo 0x800000 > address
	echo 0x10000390 > error_type
	echo 0x1 > inject

Example:

EDAC DEVICE1: CE: mdc instance: mdc0 block: mdc0 'S SRAM Rtd 1.15.4 row:28 responderID: 0xbd626f08'
		S - Single-bit error
		D - Double-bit error
		SRAM - Hardware component
		Rtd - Details from firmware
				R: UHRSN
					U - Uncorrected error, uncontainable error (UC)
					H - Uncorrected error, unrecoverable error (UEU)
					R - Uncorrected error, Latent or restartable error (UEO)
					S - Uncorrected error, Signaled or recoverable error (UER)
					N - The RAM cannot generate uncorrectable errors
				t: pt
					p - Persistent if a soft error occurs in this memory, multiple soft errors may be seen
					t - Transient if a soft error occurs in this memory, it will generally be seen only once
						Software never needs to take any action
				d: dc
					d - Deferred if a DBE occurs in this memory, the block sends out poison to the
						consumer and does not otherwise consume the data
					c - Consumed this memory is reporting it received a poison and is propagating it
		1.15.4 - chaine 1 hub 15 node 4
		row:28 - row 28
		responderID: 0xbd626f08 - RAS ID identifier Software typically uses this
									to indicate in an error record which memory
									is reporting the error
